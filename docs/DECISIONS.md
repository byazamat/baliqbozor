# Принятые решения

Формат: дата · вопрос · решение · причина. Заполняется по ходу разработки (см. SPEC.md, раздел 15).

- **D-01** · 2026-10-31 · Node 20 LTS из SPEC 5.2 · Node 24 LTS, закреплена v24.21.0 (`.nvmrc`, `engines: >=24.21.0 <25`; подтверждено владельцем) · Поддержка Node 20 закончилась в апреле 2026.
- **D-02** · 2026-10-31 · Версии стека (React 18 / Next 14+ / NestJS 10+ в SPEC 5.2) · Последние стабильные официальные версии на момент старта: Next.js 16.4, React 19.3, React Native 0.88, NestJS 12, Tailwind 4, ESLint 10, Vitest 5, Jest 30, pnpm 12, Turborepo 2; одна версия React во всём монорепозитории · Требование владельца: использовать последние официальные версии. RN 0.88 требует React ^19.3; все версии совместимы с Node 24. SPEC 5.2 обновлён.
- **D-03** · 2026-10-31 · Prisma 5 в SPEC 7.1 · Prisma 7 (7.10.1, последняя стабильная; 8.0 пока RC): генератор `prisma-client` с `output`, `url` перенесён в `packages/db/prisma.config.ts`, клиент через `@prisma/adapter-pg` · Решение владельца. В Prisma 7 `datasource url` в схеме не поддерживается; схема в SPEC 7.2 исправлена и проходит `prisma validate` 7.10.1.
- **D-04** · 2026-10-31 · Когда вводить схему БД и первую миграцию · В M0 только пакет `packages/db` (prisma.config.ts, генератор, команды `db:migrate`/`db:seed`); полная схема 7.2 и миграция `init` — первая задача M1 · Решение владельца: миграция делается в M0, только если она есть в M0 по SPEC 14.1, а там её нет.
- **D-05** · 2026-10-31 · Пути health (5.3 против префикса 10.1), health у worker · `/health` и `/ready` вне `/api/v1`; worker поднимает HTTP-сервер на `WORKER_HEALTH_PORT` · Привычно для проб оркестратора; у standalone-worker нет HTTP.
- **D-06** · 2026-10-31 · Mobile в `pnpm dev` и CI · Не входит в `pnpm dev` (скрипты `mobile:*`); в CI — lint, typecheck и jest без нативной сборки; Android-сборку в CI добавить в M10 вместе с Fastlane · Нативная сборка долгая; до M10 мобильный код почти не меняется. У владельца есть Android SDK и Xcode для локальной проверки.
- **D-07** · 2026-10-31 · Hoisting зависимостей для RN · `node-linker=hoisted` или точечный `public-hoist-pattern` — выбор по результату проверки Metro в M0.11 · Metro плохо работает с симлинками pnpm.
- **D-08** · 2026-10-31 · i18n-библиотеки · `packages/i18n` хранит JSON и форматтеры; web/admin — next-intl, mobile — i18next · ТЗ не задаёт библиотеку; общий источник ключей сохраняется.
- **D-09** · 2026-10-31 · Форматирование денег, веса и дат · Свои форматтеры без `Intl` · В Hermes `Intl` ограничен, локаль `uz` неполная; вывод должен совпадать на Node, в браузере и на Hermes.
- **D-10** · 2026-10-31 · Недостающие переменные окружения · Добавить `S3_PUBLIC_ENDPOINT`, `JWT_ACCESS_SECRET_PREVIOUS`, `WORKER_HEALTH_PORT`, `APP_DEEPLINK_SCHEME=baliqbozor`, `BRAND_NAME=BaliqBozor`; домен — только через `WEB_URL`/`ADMIN_URL`/`API_URL` · Presigned URL для браузера, ротация JWT двумя ключами (13.2), бренд и схема в конфиге (15.11); бренд и домен пока неизвестны.
- **D-11** · 2026-10-31 · Ожидающие приглашения (8.1) без модели · Новая модель `OrgInvitation(phone, orgId, role, invitedById, expiresAt, acceptedAt)` в M1 · Иначе требование 8.1 не реализовать.
- **D-12** · 2026-10-31 · Порядок milestones против зависимостей · Минимальные outbox, in-app уведомления, settings и загрузка медиа (presigned + complete) переносятся в M1; обработка медиа остаётся в M2 · Критерий M1 требует отправки документов и in-app уведомления, а M2 — напоминаний о свежести.
- **D-13** · 2026-10-31 · «Рабочее время» для SLA (8.4, 8.19) · Все дни недели рабочие, интервал `ops.workingHours` (08:00–20:00, Asia/Tashkent); календарь праздников — позже · Выходные и праздники в ТЗ не определены.
- **D-14** · 2026-10-31 · `X-Org-Id` и организация из пути запроса · Если указаны оба, они должны совпадать, иначе `FORBIDDEN` · Защита от подмены контекста организации.
- **D-15** · 2026-10-31 · STAFF продавца и `POST /listings/:id/confirm` · STAFF только подтверждает актуальность; менять `volumeKg`/`pricePerKg` могут OWNER/MANAGER · По таблице 9 STAFF лишь просматривает наличие.
- **D-16** · 2026-10-31 · TypeScript 7 (последний релиз) · TypeScript 6.0.3 · typescript-eslint поддерживает TypeScript `<6.1`, ts-jest — `<7`, openapi-typescript — `^5`; у TypeScript 7 (нативная версия) пока нет совместимого JS API. Пересмотреть, когда инструменты добавят поддержку.
- **D-17** · 2026-10-31 · PostgreSQL 16 / Redis 7 в SPEC · PostgreSQL 18, Redis 8 (последние стабильные образы) · Требование владельца о последних версиях; SPEC 5.2 и 13.5 обновлены.
- **D-18** · 2026-10-31 · Порядок второстепенных неясностей · Агент сам выбирает значение по умолчанию и записывает его сюда, не останавливая работу · Подтверждено владельцем (дополняет правило 3 в CLAUDE.md).
- **D-19** · 2026-10-31 · Пробелы и единицы в форматтерах · Разделитель тысяч и пробел перед единицей — неразрывный (U+00A0); вес: uz `kg`, ru `кг`, не больше одного знака, `,0` не показывается; сообщения API локализуются по `Accept-Language` (uz по умолчанию) · Без переносов внутри чисел; SPEC 12.1 не задаёт русскую единицу веса.
- **D-20** · 2026-10-31 · Модульная система бэкенда · NestJS 12 распространяется только как ESM → все пакеты и api/worker — ESM (`type: module`, `nodenext`); Jest 30 + ts-jest в ESM-режиме (`--experimental-vm-modules`); правило «нет литералов в JSX» — собственное (`baliqbozor/no-jsx-literals`), т.к. eslint-plugin-react не поддерживает ESLint 10 · Совместимость с последними версиями.
- **D-21** · 2026-10-31 · Образ MinIO · Официальные `minio/minio`/`minio/mc` больше не публикуются на Docker Hub; используется форк `pgsty/minio` (тот же API и `mc` внутри) · Требуется S3-совместимое хранилище локально; код работает через `StorageProvider` и не зависит от выбора. Пересмотреть при подготовке staging (M11).
- **D-22** · 2026-11-01 · «Пресет Tailwind» в Tailwind 4 · Пресет — CSS-файл `packages/ui/src/theme.css` с блоком `@theme` (токены цветов, радиусов, шрифта); приложения подключают его `@import` и указывают `@source` на `dist` пакета; контраст пар текст/фон (≥ 4.5) и рамок/фокуса (≥ 3) проверяется тестом, который читает тот же CSS · В Tailwind 4 JS-пресеты устарели; один источник токенов без генерации.
- **D-23** · 2026-11-01 · Устройство worker в M0 · Health-сервер — `node:http` без Express (только `GET /health`, `/ready`: БД и Redis); одно подключение ioredis (`maxRetriesPerRequest: null`) на BullMQ и проверку готовности, префикс ключей `bq`; outbox опрашивается циклом без наложений (полная пачка — сразу следующая, иначе пауза `OUTBOX_POLL_INTERVAL_MS`, пачка `OUTBOX_BATCH_SIZE`), источник — интерфейс `OutboxSource` (реализация на Prisma с `FOR UPDATE SKIP LOCKED` — в M1, когда появится `DomainEvent`); `msgpackr-extract` (нативный ускоритель bullmq) добавлен в `allowBuilds` · Минимум зависимостей; интервалы — настройки окружения.
- **D-24** · 2026-11-01 · Локаль в URL для web/admin · next-intl с `localePrefix: 'as-needed'`: uz без префикса (`/catalog`), ru — `/ru/catalog`; admin устроен так же (без индексации: `robots: noindex`) · Пути из SPEC 12.2 остаются как есть для языка по умолчанию, у русской версии свои URL для поиска; один подход в обоих приложениях. Корневой `.env` читается в `next.config.ts`; бренд — `NEXT_PUBLIC_BRAND_NAME` (D-10). `@swc/core` (зависимость next-intl) добавлен в `allowBuilds`.
- **D-25** · 2026-11-01 · Мобильное приложение в монорепозитории (закрывает D-07) · pnpm в изолированном режиме без `node-linker=hoisted`: Metro следит за корнем репозитория (`watchFolders`) и ищет модули в `node_modules` приложения и корня; `@react-native/gradle-plugin` и `@react-native/codegen` — прямые devDependencies, чтобы Gradle нашёл их по путям шаблона. Идентификатор приложения — `uz.baliqbozor.app` (рабочий, сменить вместе с брендом). Адрес API в debug: Android-эмулятор `http://10.0.2.2:4000`, iOS — `http://localhost:4000`; релизный адрес — в M11. Язык в M0 не сохраняется между запусками (хранилище появится вместе с токенами в M1). Отклонения от «последних версий»: Jest 29.7 и Babel 7.29 — `@react-native/jest-preset` 0.88 зависит от `babel-jest` 29, плагины пресета — Babel 7 · Проверено: Metro-бандл, `assembleDebug` и запуск на эмуляторе.
- **D-26** · 2026-11-01 · Устройство CI · GitHub Actions, три параллельных job'а на `ubuntu-latest`: `checks`, `e2e`, `web-e2e`; общая подготовка — composite-action `.github/actions/setup` (Node из `.nvmrc`, pnpm из `packageManager`, `--frozen-lockfile`, `.env` из `.env.example`). Actions закреплены по мажорной версии (checkout v7, setup-node v7, pnpm/action-setup v6, upload-artifact v7). `lint` в `db` и `i18n` сначала генерирует код: на чистом клоне сгенерированных файлов нет · Одинаковое окружение локально и в CI; проблема с генерацией найдена прогоном на чистом клоне.
- **D-27** · 2026-11-01 · Итоги проверки M0 на чистом клоне · (1) Логирование: маскирование телефонов (`maskPhonesDeep` в `packages/domain`) обходит только простые объекты и массивы — pino вызывает `formatters.log` до сериализаторов, и копия `ServerResponse` теряла `headersSent`, отсюда `statusCode: null`; ответ логируется только кодом статуса. (2) Скрипты, зависевшие от локальных артефактов: `lint` в web/admin сначала выполняет `next typegen`, `db:seed` — `prisma generate`, `api:generate` собирает сам api (`--filter=@baliqbozor/api...`). (3) `pnpm infra:up`: `docker compose up --wait` возвращает 1 из-за завершившегося `minio-init`, поэтому сначала ждём postgres/redis/minio, затем `run --rm minio-init`; CI использует тот же скрипт · Первый прогон CI упал на lint и запуске инфраструктуры; локальная проверка маскировала коды выхода.
- **D-28** · 2026-11-01 · Хозяйство перед верификацией продавца (8.1 п. 3) в M1 · В M1 отправка документов не требует хозяйства; правило «минимум одно хозяйство у продавца» включается в M2 вместе с хозяйствами · Хозяйства — содержание M2, а критерий M1 требует верификации продавца.
- **D-29** · 2026-11-01 · Кто отправляет документы на верификацию · `SELLER` и `CARRIER` — обязательно для работы; `BUYER` может отправить по желанию, обязательной проверки нет (8.1 п. 6), оператор может верифицировать покупателя и без документов · Покупатель по SPEC проходит модерацию первой заявки, а не организации.
- **D-30** · 2026-11-01 · Повторная отправка и правка после решения · После `REJECTED` можно исправить данные и отправить снова (`PENDING`, новая задача `VERIFY_ORG`); пока `PENDING`, повторная отправка — `INVALID_TRANSITION`; правка юридических полей (`type`, `legalForm`, `name`, `tin`) у `VERIFIED` возвращает статус в `UNVERIFIED` только через оператора — владелец эти поля у `VERIFIED` не меняет · Проверенные данные не должны меняться без проверки.
- **D-31** · 2026-11-01 · Хранение токенов в web/admin · API отдаёт токены в теле (SPEC 10.3); web и admin держат refresh-токен в httpOnly-cookie (SameSite=Lax, Secure вне local) через собственные route handlers Next.js, access-токен — только в памяти · Refresh-токен недоступен JS страницы (защита от XSS), контракт API не меняется.
- **D-32** · 2026-11-01 · Формат телефона · В MVP только номера Узбекистана: хранение `+998XXXXXXXXX`, ввод с маской `+998 90 123 45 67`, нормализация пробелов/скобок/дефисов · SPEC 7.2 и 12.1 задают этот формат.
- **D-33** · 2026-11-01 · Каналы уведомлений в M1 · Только `IN_APP`; событие `org.member.invited` отправляет SMS через `SmsProvider` (в M1 — console) без записи `Notification`, если у номера ещё нет пользователя; push, Telegram и Eskiz — M8/M10; настройки уведомлений (`/me/notification-preferences`) — вместе с появлением второго канала · Иначе пришлось бы делать каналы, которые некуда доставить.
- **D-34** · 2026-11-01 · Обновление счётчика уведомлений до realtime · Web опрашивает `GET /notifications` (только `unreadCount`) раз в 30 с и при фокусе окна; Socket.IO — в M4 · Realtime по плану SPEC в M4; p95 ≤ 30 с выполняется опросом.
- **D-35** · 2026-11-01 · Настройки вне таблицы 8.13 · В реестр настроек добавляется `order.requireVetDocument = false` (SPEC 15, п. 7); прочие ключи — только по мере надобности с записью сюда · Единый источник настроек.
- **D-36** · 2026-11-01 · Первые операторы и администраторы · Локально и на staging — из seed (номера `+998900000001…`, вход через `OTP_DEV_BYPASS_CODE` только при `APP_ENV=local`); на staging/production платформенная роль выдаётся командой `pnpm admin:grant <phone> <OPERATOR|ADMIN>` (с записью в аудит) · В SPEC не описано, как появляется первый администратор.
- **D-37** · 2026-11-01 · Карты (выбор точки хозяйства и адреса, карта кандидатов) · OpenStreetMap через Leaflet, тайлы по URL из настройки окружения (`NEXT_PUBLIC_MAP_TILE_URL`, атрибуция обязательна); компонент карты за общим интерфейсом, чтобы позже сменить провайдера (Яндекс/Google) без переделки экранов · Решение владельца: бесплатный вариант на старте. Публичный сервер тайлов OSM имеет политику честного использования — для production предусмотреть свой или платный тайл-сервер (M11).
- **D-38** · 2026-11-01 · Частичные уникальные индексы `PriceIndex` и генерация кода · (1) Вместо ручного SQL в миграции — preview-функция Prisma 7.10 `partialIndexes` (`@@unique(..., where: raw(...))`): индексы видны Prisma, `migrate dev`/`migrate diff` не считают их расхождением. Prisma выдаёт их как обычные составные ключи `findUnique`/`upsert`, но без условия `regionId IS NULL` — в коде ценового индекса (M11) искать строки только `findFirst` с явным `regionId`. (2) Проверка «схема = миграции» в CI — `migrate deploy` на пустую БД и `migrate diff --from-config-datasource --to-schema --exit-code`: не нужна теневая БД. (3) Генерация (Prisma, сообщения i18n, `next typegen`) — turbo-задача `generate`, от которой зависят остальные задачи; скрипт генерации типов api-client переименован в `generate:types`, чтобы не входить в неё · Параллельные `prisma generate` в одном пакете портили сгенерированные файлы; preview-функцию снять, когда станет стабильной.
- **D-39** · 2026-11-01 · Уточнения правил M1 · (1) Тип организации (`SELLER/BUYER/CARRIER`) после создания не меняется никем — иначе ломаются хозяйства, заявки и заказы; для другого типа создаётся новая организация. (2) Снятие блокировки (`UNSUSPEND`) возвращает `VERIFIED`, если организация уже проходила верификацию (`verifiedAt` задан), иначе `UNVERIFIED` — отдельного поля «прежний статус» в схеме нет. (3) Покупателя оператор может верифицировать из `UNVERIFIED`/`REJECTED` без заявки (8.1 п. 6); продавца и перевозчика — только из `PENDING`. (4) Адреса доставки: видят все члены организации-покупателя, меняют OWNER/MANAGER (в SPEC 9 строки нет; STAFF покупателя оформляет приёмку и должен видеть адрес). (5) Новые настройки: `otp.maxPerIpPerHour = 20` и `otp.blockMinutes = 60` (числа из SPEC 13.2), `org.invitationTtlDays = 30` · Закрывают неясности SPEC 8.1, 9 и 13.2 значениями по умолчанию, вынесенными в настройки.
- **D-40** · 2026-11-01 · Инфраструктура API (M1.2) · (1) Outbox: служебное поле `DomainEvent.availableAt` — аренда события на 60 с при захвате (`FOR UPDATE SKIP LOCKED`) и пауза перед повтором (5 с × 2ⁿ, до 10 мин); после 10 неудач событие не обрабатывается и ждёт разбора (алерт SPEC 13.3 — M11); обработчик и отметка «обработано» — в одной транзакции. (2) Лимит запросов — guard с фиксированным минутным окном в Redis, ключ — пользователь, до входа — IP; на несуществующие маршруты не действует (их отдаёт роутер); при недоступности Redis запросы пропускаются; число — `RATE_LIMIT_PER_MINUTE` в env (инфраструктурная, не бизнес-настройка). (3) Кэш настроек — Redis 5 мин со сбросом при изменении; без Redis читается БД. (4) e2e работают на отдельной БД `<имя>_test` и Redis `/1` — тесты не трогают данные разработки. · Надёжная доставка без дублей между worker'ами; API не падает из-за Redis; тесты воспроизводимы.
